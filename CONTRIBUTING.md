# Как попасть в каталог

Путь один: предложение → ревью → публикация. Ручных исключений нет, потому что исключение из процесса быстро становится процессом.

## 1. Предложение

Заведи issue с ответами на пять вопросов:

1. Какую повторяющуюся работу это закрывает и как часто она возникает?
2. Откуда взята процедура — чья практика, какой прогон, какой разбор?
3. Что должно получаться на выходе и как проверить, что получилось верно?
4. Какие шаги обязаны быть детерминированными?
5. Что в наработке приватное и должно быть вычищено перед публикацией?

Предложение без ответа на второй вопрос не рассматривается. Скилл, выведенный из общих соображений, а не из практики, — это пересказ модели самой себе.

## 2. Работа

```bash
git checkout -b plugin/<имя>
python3 scripts/new_plugin.py <имя> --skill <скилл> --owner <владелец> --reviewer <ревьюер>
```

Заполни `SKILL.md`, `meta.json` (особенно `provenance`), evals и, если есть детерминированные шаги, `scripts/`. Перед PR:

```bash
python3 scripts/build_marketplace.py
python3 scripts/verify_repo.py
```

## 3. Ревью

PR смотрит ревьюер из `meta.json`; он не может совпадать с владельцем для статуса `production`. Ревьюер идёт по [чеклисту](docs/review-checklist.md) и обязан проверить главное: воспроизводится ли результат на реальном примере, а не выглядит ли текст скилла убедительно.

В PR приложи вывод верификатора и один настоящий прогон: вход, артефакт, что оказалось не так.

## 4. Публикация

После merge плагин появляется в витрине автоматически — `marketplace.json` пересобирается из `plugins/`. Статус переводится в `production` только после того, как плагин отработал на реальной задаче хотя бы один раз, и в `meta.json` проставлен `reviewed_at`.

## Что не берём

- Наработки под один разовый случай, которые не повторятся.
- Скиллы, которые нельзя выполнить без доступа к приватной инфраструктуре.
- Журналы выполненной работы, оформленные как процедура.
- Всё, что содержит чужие персональные данные или содержимое клиентских документов.
